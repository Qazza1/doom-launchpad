# Static-Site UI Integration Plan

## Constraints

- Preserve the current static HTML/JavaScript architecture.
- Use the wallet/provider pattern already present in the site; do not add Next.js.
- Keep public risk facts and launch/lock/commitment facts visible without NFT gating.
- Never describe failed creator allocations as buyer protection.
- Do not enable testnet transaction buttons until verified addresses and ABI artifacts are configured.

## Proposed file layout

```text
site/
  launchpad/
    launch.html
    launch-detail.html
    gm.html
    rewards.html
    doom-launchpad.css
    doom-launchpad.js
    doom-launchpad-abi.js
    doom-launchpad-config.js
```

These may later be folded into the existing single-page tab system, but separate static pages reduce regression risk during testnet development.

## 1. Launch wizard

### Step 1 — Token

- Name, symbol, fixed supply.
- Plain-language confirmation: no future minting, taxes, blacklist, or owner controls.
- Client validation mirrors contract length/supply rules but never replaces on-chain validation.

### Step 2 — Allocations

- Three inputs totaling exactly 100%:
  - creator liquid
  - initial liquidity
  - GM escrow
- Live token-amount preview using integer arithmetic.
- Explicit note that the escrow allocation goes to community rewards on finalized default.

### Step 3 — GM commitment

- Required check-ins, cadence, grace period.
- Render exact first due time and every scheduled window before signature.
- Warn that late check-ins do not shift future windows.

### Step 4 — Liquidity and lock

- Native liquidity amount.
- Supported fee-tier selector populated only from verified config.
- Price/range presets generated by reviewed utilities; advanced raw ticks hidden behind an expert disclosure.
- Lock duration and fixed beneficiary policy.
- Show expected position-manager, locker, and configuration hash.

### Step 5 — Review

- Human-readable transaction summary.
- Total native value = launch fee + liquidity.
- No default values for unresolved economics.
- Wallet simulation/estimate before enabling submit.
- Require correct chain ID and non-placeholder addresses.

### Step 6 — Result

- Transaction hash, token, pool, escrow, position ID, locker, and indexer confirmation state.
- Links to launch detail, GM page, token analytics, and explorer.

## 2. Launch detail page

Public panels:

- Token identity and existing OnchainDiligence risk score/signals.
- Creator history and prior launch outcomes.
- Allocation breakdown.
- Commitment badge and schedule.
- LP lock owner, position ID, unlock time, beneficiary, and configuration hash.
- Reward funding/campaign state after default.
- Raw contract/explorer links.
- Clear statement: indicators are not a guarantee of safety.

Token-detail links should connect both ways:

- Existing token detail → Doom Launchpad launch record.
- Launch detail → existing risk/holder/liquidity/creator analytics.

## 3. GM countdown page

- Read escrow state directly from chain, with indexer as a cached enhancement.
- Display current scheduled check-in time, deadline, and chain timestamp reference.
- States:
  - `Not open yet`
  - `GM window open`
  - `Default eligible — not finalized`
  - `Completed`
  - `Defaulted`
- Creator-only button for `recordGm()`.
- Permissionless `Finalize default` button only after the contract deadline.
- Disable based on a fresh contract read, never only local clock.

## 4. NFT reward claim page

- Campaign token, Merkle root, total allocation, claim deadline, and unclaimed treatment.
- Connect wallet and fetch proof from a signed/static campaign manifest endpoint.
- Locally recompute the leaf and verify proof before enabling claim.
- Query `hasClaimed(campaignId, account)` directly.
- Submit `claim(campaignId, account, amount, proof)`.
- Support relayed submission later without changing recipient.
- No loop over NFTs or holders.

## 5. Badge implementation

| Badge | Source of truth | UI behavior |
|---|---|---|
| Commitment active | Escrow status + current deadline | Countdown; distinguish late/default-eligible |
| Commitment completed | Escrow status/event | Show released amount and completion time |
| Commitment defaulted | Escrow status + verified rewards deposit | Show community reward inventory/campaign link |
| LP locked | Locker record + ERC-721 owner | Show unlock time and beneficiary |

Do not infer LP lock only from launchpad address. Verify the specific position and locker.

## 6. Static JavaScript approach

- Continue using a browser-loaded ethers bundle compatible with the existing site.
- Keep ABI/config in versioned plain JS objects.
- Use `BigNumber`/string arithmetic for all supply and amount values; never JavaScript floating point.
- Escape token name/symbol and API content before inserting into HTML.
- Use `provider.getBlock('latest')` timestamp for deadline presentation where practical.
- Reject placeholder/zero addresses and unsupported chain IDs before transaction construction.
- Add Content Security Policy review before enabling wallet actions.

## 7. Rollout

1. Read-only testnet launch detail and badges.
2. Read-only GM/reward pages with fixture campaigns.
3. Launch wizard behind an explicit testnet feature flag.
4. Creator GM transaction button.
5. Permissionless default and claim actions.
6. Usability/security review, then limited testnet cohort.

No existing homepage/indexer file is modified by this deliverable.
